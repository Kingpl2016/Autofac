Art-Net 与 sACN 协议详解

舞台灯光控制 · DMX512 over Ethernet · 网络架构 · 报文解析 · 工程部署

Art-Net 和 sACN 是舞台灯光、建筑照明、LED 像素控制、媒体服务器以及大型演出控制系统中最重要的两种基于 IP 网络的灯光控制协议。

两者的核心目标相同：

通过以太网传输多个 DMX512 Universe（域）的控制数据，让一条网络链路能够控制大量灯具，而不再受传统 DMX512 单条总线 512 通道的限制。

但两种协议在设备发现、寻址方式、数据分发、多控制源仲裁、同步机制及网络管理上存在显著区别。

一、先理解 DMX512、Universe 和以太网的关系

1. DMX512 是什么？

DMX512 是灯光控制领域的数字控制协议，通常采用 RS-485 物理层。

  • 物理通信速率：250 kbit/s。
  • 一个 DMX Universe 最多具有 512 个数据通道。
  • 常见通道值：0～255，即 8 bit。
  • 主要采用控制器向灯具连续发送数据的模式。
  • 一个标准满载 Universe 的典型最高刷新率约为 44 Hz。

例如，一个 RGB LED 灯具需要 3 个 DMX 通道：

通道功能数值
CH1Red 红色255
CH2Green 绿色128
CH3Blue 蓝色0

这样一个灯具显示的颜色就是红色较强、绿色中等、蓝色关闭。

一个 Universe 理论上可控制：

\[\left\lfloor\frac{512}{3}\right\rfloor=170\]

即 170 个独立 RGB 像素（共占用 510 通道）。

如果是 RGBW（4 通道），则为 128 个像素。

2. 为什么需要 Art-Net 和 sACN？

假设一个大型 LED 项目使用 30,000 个独立 RGB 像素。

需要的 DMX 通道数量：

\[30000\times3=90000\]

需要的 Universe：

\[\left\lceil\frac{90000}{512}\right\rceil=176\]

实际按不跨 Universe 的完整 RGB 像素分配，则需要：

\[\left\lceil\frac{30000}{170}\right\rceil=177\]

传统 DMX512 系统需要大量物理输出端口和布线。

采用 Art-Net 或 sACN，可以通过千兆以太网把 177 个 Universe 的数据传送到多个网络节点，再转换为 DMX512 或 LED 像素信号。

这里有一个非常重要的概念：

Universe 是逻辑通道组，不等于一条网线，也不必然等于一个物理 DMX 输出端口。

  • 1 个 sACN Universe 可以被 20 台接收设备订阅。
  • 1 个 Art-Net Universe 可以通过单播发送到多个 Node。
  • 一个 Node 可以接收多个 Universe，并将其映射到多个 DMX 端口。
  • LED 像素控制器也可以直接解析 DMX 数据并驱动 LED，不必转换成物理 DMX512 信号。

二、Art-Net 协议详解

1. Art-Net 是什么？

Art-Net 由 Artistic Licence 开发，是用于在以太网中传输 DMX512、设备控制和 RDM 数据的协议。

其主要特点：

  • 基于 UDP/IP。
  • 使用 UDP 端口 6454。
  • 可以进行设备发现。
  • 支持节点配置和管理。
  • 支持 RDM 相关数据传输。
  • 支持 Universe 同步和多源数据合并。
  • Art-Net 4 的地址结构理论上提供 32,768 个 Port-Address。

Art-Net 4 规范强调 ArtDmx 数据的单播传输；早期版本中的广播方式仍可能出现在旧设备或兼容实现中。参考资料

4. Art-Net 设备发现机制

Art-Net 的一项重要优势是具有设备发现机制。

典型通信流程：

具体过程：

  1. Controller 发送 ArtPoll 请求发现设备。
  2. Node 通过 ArtPollReply 返回节点信息。
  3. Controller 获得节点 IP、端口、Universe、能力等数据。
  4. Controller 确定哪些 Node 需要哪些 Universe。
  5. Controller 将 ArtDmx 数据以单播方式发送给目标 Node。

这使 Art-Net 很适合需要自动扫描、配置和管理灯光节点的系统。

6. ArtDmx 数据包结构

ArtDmx 是 Art-Net 最重要的数据包，负责真正传输通道值。

典型 ArtDmx 报文由 18 字节头部和 2～512 字节 DMX 数据组成。

字节偏移字段长度
0–7ID：Art-Net\08 Byte
8–9OpCode：0x50002 Byte
10–11ProtVer2 Byte
12Sequence1 Byte
13Physical1 Byte
14–15Port-Address2 Byte
16–17Length2 Byte
18 起DMX 数据2～512 Byte

其中：

  • Sequence：帮助接收端处理数据包顺序；0 代表禁用序号功能。
  • Physical：发送源物理输入端口标识。
  • Port-Address：本帧所属的 Universe。
  • Length：本次携带的数据长度。
  • Data：DMX 通道值。

标准满载 ArtDmx UDP 负载大小：

\[18+512=530\ \text{Byte}\]

加上 IPv4 和 UDP 头部（通常合计 28 字节，不含 IP 选项）：

\[530+28=558\ \text{Byte}\]

即一个完整 Universe 的 ArtDmx 报文在 IP 层通常是 558 字节。此数值还不包括以太网帧头、FCS、帧间间隔等链路开销。

7. ArtSync 同步机制

假设 LED 显示系统有 10 个 Universe。

如果它们分别在不同时刻更新，可能造成一部分像素显示新画面，另一部分仍显示旧画面。

ArtSync 用于协调更新。

Controller
   |
   +-- Universe 1 新数据
   +-- Universe 2 新数据
   +-- Universe 3 新数据
   +-- Universe 4 新数据
   |
   +-- ArtSync 同步触发
             |
             v
       Node 协同更新输出

但要注意：

ArtSync 并不等于硬件级帧同步或视频 Genlock。最终刷新的一致性仍与节点缓冲、处理延迟、输出方式及设备实现有关。

三、sACN 协议详解

1. sACN 是什么？

sACN，全称 Streaming Architecture for Control Networks，通常指 ANSI E1.31 定义的流式 DMX512 传输协议。

它使用 ACN 协议体系的一部分，在 IP 网络中传输 DMX512 数据。

截至 2026 年 10 月，标准版本为 ANSI E1.31-2025，于 2026 年正式发布。这个版本包括 IPv4 与 IPv6 支持。参考资料

sACN 的主要特点：

  • 以 UDP/IP 传输数据。
  • 使用 UDP 端口 5568。
  • 支持组播 Multicast 和单播 Unicast。
  • IPv4 下，Universe 对应特定组播地址。
  • 支持多个数据源的优先级仲裁。
  • 支持数据序列编号。
  • 支持多 Universe 同步。
  • 使用 CID 标识发送源。
  • 具有 Universe Discovery 机制。

2. sACN 的 Universe 地址

sACN 常用 Universe 编号范围为：

\[1\sim63999\]

即最多 63,999 个可用 Universe 编号。

这一数字是逻辑寻址能力，不代表一台控制器可以实际同时输出 63,999 个 Universe。

3. sACN 组播机制

这是 sACN 与 Art-Net 最重要的区别之一。

对于 IPv4，sACN 的每个 Universe 对应一个组播地址。

地址计算为：

\[IP=239.255.H.L\]

其中：

\[H=\lfloor U/256\rfloor\]

\[L=U\bmod256\]

U 为 Universe 编号。

例如：

Universe组播地址
1239.255.0.1
2239.255.0.2
15239.255.0.15
256239.255.1.0
512239.255.2.0
1024239.255.4.0
63999239.255.249.255

所有上述数据报的 UDP 目的端口通常均为 5568。

4. 为什么 Multicast 很重要？

假设一个 Universe 需要同时发送给 20 台 LED 控制器。

Unicast 单播：

控制器

每个目标都有自己的单播数据流（图中示意 10 个目标）

假设一份 Universe 的数据流为 200 kbit/s，20 台接收设备都订阅同一份数据，发送端可能需要输出约：

\[200\ \text{kbit/s}\times20=4\ \text{Mbit/s}\]

Multicast 组播：

↓

在同一组播域内，控制器通常只需要发送一份数据，交换机负责向需要它的下游端口复制。

因此，组播可以降低源端发送量。

但有一个重要前提：

Multicast 不一定天然减少接收端负担。

如果交换机不能正确执行 IGMP Snooping，组播流量可能被泛洪到不需要接收的端口。

所以在大型 sACN 项目中，交换机的 IGMP Snooping、IGMP Querier、VLAN 设计十分重要。

6. sACN Priority 优先级

这是 sACN 在多控制源系统中非常重要的一项能力。

Priority 可使用 0～200 的数值，通常默认值为 100。

数值越高，优先级越高。

例如，同时有两套系统控制舞台 Universe 1：

数据源PriorityDimmer CH1
主控灯光台1500
建筑照明控制器100255

通常应采用更高优先级数据源的控制值：

\[CH1=0\]

这里不能简单地使用最大通道值 255。

因为 Priority 的选择先于常规同级 HTP 合并。

ETC 的灯光控制文档也明确说明，高优先级源可以覆盖低优先级源，即使其输出的亮度更低。

7. sACN 合并：Priority、HTP 与 PAP

需要区分三个概念。

Priority（优先级）

决定哪一个发送源优先获得控制权。

HTP（Highest Takes Precedence）

多个合格源的同一个通道取最大值。

例如：

\[HTP(100,200)=200\]

PAP（Per-Address Priority）

每地址优先级扩展允许不同 DMX 通道使用不同优先级，而不必整个 Universe 使用同一个优先级。

例如：

通道主控台优先级建筑控制器优先级结果来源
CH1150100主控台
CH2100160建筑控制器
CH3120120依同优先级合并策略

PAP 对建筑照明与演出灯光共用同一 Universe 的场景特别有用。

注意：具体接收器是否支持 PAP、支持多少个并发源，以及合并方式如何，都需要检查设备说明书。不能假定所有标称支持 sACN 的设备都完整支持高级功能。

8. sACN Sequence Number

sACN Data Packet 具有 8 位 Sequence Number：

\[0\sim255\]

发送时递增，到 255 后回绕至 0。

它可帮助接收端检测数据包乱序、重复和丢失。

但需要理解：

  • UDP 不保证送达。
  • sACN 不进行 TCP 式重传。
  • Sequence Number 不等于数据可靠传输保证。
  • 实时灯光控制通常宁愿使用最新数据，而不是等待旧数据重传。

9. sACN Synchronization

sACN 也可以对多个 Universe 执行同步。

工作过程：

Source
  |
  +-- Universe 1 Data
  +-- Universe 2 Data
  +-- Universe 3 Data
  |
  +-- E1.31 Synchronization Packet
                  |
                  v
         Receivers 更新数据

实现同步时，数据包中还会涉及 Synchronization Address 等字段。

适合的应用包括：

  • 大面积 LED 像素矩阵。
  • 多区域动态光效。
  • 多 Universe 同步变色。
  • 大型建筑媒体立面。

与 ArtSync 一样，协议层同步不能消除所有设备和灯具级输出延迟。

两个协议并不存在绝对的性能胜负，主要看网络拓扑、接收设备数量、功能支持和实施质量。

重要区别：sACN Universe Discovery 并不是 ArtPoll 的完全等价替代。

sACN 的发现机制主要用于让接收方了解哪些源正在发送哪些 Universe；它本身不提供 Art-Net 那样完整的节点配置、IP 管理与 RDM 通道。

因此，设备管理和灯光数据分发可以采用不同协议。

Art-Net 4 本身也支持以 Art-Net 进行节点管理、以 sACN 进行控制数据传输的组合思路。

五、网络带宽与 Universe 数量计算

1. 单个 Universe 消耗多少带宽？

假设：

  • 每个 Universe 包含 512 个 DMX 通道。
  • 更新频率为 40 Hz。
  • IPv4 无选项。
  • 无 VLAN 标签。
  • 按千兆以太网常规封装估算。

计算链路占用时，应计入：

  • UDP Header：8 字节。
  • IPv4 Header：20 字节。
  • Ethernet Header：14 字节。
  • FCS：4 字节。
  • Preamble 与 SFD：8 字节。
  • Inter-Frame Gap：12 字节。

Art-Net 典型每帧链路占用：

\[530+8+20+14+4+8+12=596\ \text{Byte}\]

单 Universe、40 Hz：

\[596\times8\times40=190720\ \text{bit/s}\]

约 0.191 Mbit/s。

sACN 相应为：

\[(638+66)\times8\times40=225280\ \text{bit/s}\]

约 0.225 Mbit/s。

2. 不同 Universe 数量的带宽需求

理论链路负载对比
40 Hz、满载 512 通道、IPv4、常规以太网封装；不包含重传、其他业务及复制流量。

以上是每个 Universe 仅发送一份数据时的估算。

假设一个项目：

  • 500 个 Universe。
  • 40 Hz 刷新率。
  • 所有 Universe 都采用满载数据。
  • 发送端对每个 Universe 只发送一份流。

理论发送负载约为：

  • Art-Net：95.36 Mbps。
  • sACN：112.64 Mbps。

所以，100 Mbps 链路对这个 sACN 示例已经不够用，而 1 Gbps 链路通常有充分余量。

但这不意味着 1 Gbps 端口就能稳定承载按除法算出的全部 Universe。必须考虑端口汇聚、突发流量、设备接收能力、多个发送源、组播复制和其他网络业务。

2. IGMP Snooping 与 Querier

对于 sACN 组播网络，建议重点理解：

IGMP Snooping

交换机监听接收器加入哪些组播组，然后将相应流量转发到有接收器的端口。

IGMP Querier

定期查询组播成员关系，帮助交换机维护正确的端口与组播组映射。

典型配置：

Lighting VLAN: 20

IGMP Snooping: Enable
IGMP Querier:  Enable

Source:
10.20.0.10

Multicast Group:
239.255.0.1
239.255.0.2
239.255.0.3
...

部署时应确认：

  1. 同一 VLAN 中 Querier 的工作状态。
  2. 接收节点是否实际发出 IGMP Join。
  3. Snooping 表是否建立正确成员关系。
  4. 交换机是否正确处理未知组播。
  5. 是否出现组播流量泛洪或被错误过滤。

此外，要区分 IGMPv2/IGMPv3 的兼容性，以及交换机对 239.255.0.0/16 管理范围组播的处理策略。

3. VLAN 是否必要？

小型独立灯光网络未必一定需要 VLAN。

对于大型工程，推荐使用 VLAN 对不同业务进行逻辑隔离。

例如：

VLAN用途
VLAN 10控制与设备管理
VLAN 20Art-Net / sACN 数据
VLAN 30媒体服务器相关网络
VLAN 40监控和工程维护

需要特别强调：

VLAN 并不会自动保证灯光数据的实时性，也不能代替合理的带宽与交换机设计。

跨 VLAN 的 sACN 组播传输，还需要额外的三层组播路由或明确的转发策略，不能假定配置了 VLAN 就能跨网段接收。

3. 如何判断是不是网络丢包？

仅仅看到灯具闪烁，不能直接认定为网络丢包。

建议按照下列顺序定位：

  1. 在控制器发送端抓包，确认输出是否正常。
  2. 在目标 Node 所接交换机端口镜像抓包。
  3. 比较两个位置收到的数据流、序列号和间隔。
  4. 检查交换机端口的丢包、CRC、接口速率及拥塞统计。
  5. 检查 Node 的接收统计和缓冲行为。
  6. 最后检查实际 DMX512 波形、终端电阻、灯具地址及电源。

采用这种分层排查方式，可以区分软件输出、网络转发、节点处理和灯具侧故障。

八、两种协议应该如何选型？

⚙
优先考虑 Art-Net 的情况

需要扫描并配置大量 Art-Net Node、使用 Art-Net 设备管理及 RDM 功能，或项目已有成熟 Art-Net 设备体系。应优先使用符合较新规范的单播实现。

◇
优先考虑 sACN 的情况

多个接收器共享相同 Universe，要求以组播高效分发，或存在建筑照明与演出控制系统之间的优先级仲裁需求。

⇄
同时采用 Art-Net 和 sACN 的情况

利用 Art-Net 的发现和节点管理能力，同时用 sACN 分发实际的 DMX 数据。前提是相关控制器与 Node 均支持所需混合工作模式，并处理好 Universe 映射。

九、针对控制器与软件开发的建议

如果需要自行开发 Art-Net / sACN 控制软件，建议把传输协议和灯具控制逻辑分开设计。

              Application Layer
          Scene / Timeline / Effects
                       |
              DMX Universe Engine
                       |
             512-Channel Buffers
                       |
                Output Scheduler
                       |
              Protocol Abstraction
                 /           \
             Art-Net         sACN
                |              |
           UDP 6454        UDP 5568
                 \           /
                   Ethernet

推荐的软件模块划分：

模块主要职责
Universe ManagerUniverse 创建、编号、映射
DMX Buffer各 Universe 的 512 通道缓存
Output Scheduler控制发送周期和帧更新
Art-Net Encoder生成 ArtDmx、ArtPoll 等报文
sACN Encoder生成 E1.31 Root/Framing/DMP
Source Manager管理 CID、源状态和优先级
Sync Manager协调多 Universe 输出
Network Manager网卡、单播目标和组播成员管理
Diagnostics丢包、延迟、序号及流量统计

开发时需要特别注意：

  • 不要将 Universe 编号误当成 DMX Channel 地址。
  • 不要假设 Art-Net 和 sACN 使用相同的报文大小或字节序。
  • sACN 发送源应维护稳定的 CID。
  • 每个 Universe 应维护正确的序列号状态。
  • 接收端要处理多个发送源的超时及优先级切换。
  • 发送线程不应因为界面渲染或其他业务阻塞。
  • 高 Universe 数量下，要关注操作系统 UDP 发送缓冲、定时精度以及报文突发。

对于大型实时灯光系统，比单纯提高网络速率更重要的是建立可预测的调度、同步和拥塞控制机制。

最终结论

Art-Net 的核心优势是 节点发现、设备配置与控制数据传输的整合能力。

sACN 的核心优势是 标准化的 Universe 数据分发、组播以及多控制源优先级控制。

对于现代大型灯光或 LED 像素系统，推荐优先评估 sACN 作为实时控制数据协议，并根据设备管理需求配合 Art-Net；如果现有设备、控制平台和操作流程已经高度依赖 Art-Net，使用设计正确的 Art-Net 单播网络也完全合理。

真正决定系统稳定性的不是协议名称，而是 Universe 映射、收发能力、网络拓扑、组播管理、同步策略和故障诊断能力。
